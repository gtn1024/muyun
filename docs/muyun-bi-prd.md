# MuYun BI 快速开发平台 (muyun-bi) 产品需求文档 (PRD)

## 1. 产品概述

### 1.1 产品背景
MuYun 是一个采用 JVM 系第一梯队性能（Java 21 + Quarkus）、云原生、前后端分离的“后端优先”轻代码开发平台。当前平台已具备成熟的模块注册、功能/数据权限治理、标准增删改查（CRUD）、扩展能力（日志、文件管理、动态表构建等）和运行时环境接入能力。

为进一步赋能企业级应用，我们计划以“基础能力包”的形式引入 `muyun-bi`。它旨在打破传统 CRUD 限制，提供一层能够描述多维交叉分析、聚合查询以及数据可视化编排的“语义与查询层”，使开发者能在 MuYun 平台内快速组装数据报表和仪表盘。

### 1.2 产品定位
**Developer-first 的轻代码敏捷 BI 能力基座。**
- **非定位:** 取代极度复杂、支持无限拖拽的商业级全能 BI（如 Tableau 或 FineBI）。
- **定位:** 作为 MuYun 生态下的基础能力组件，提供从数据接入、语义建模、查询编译到图表渲染、看板发布端到端的标准化框架，供中后台与分析系统快速调用展现。

### 1.3 核心目标
1. **统一数据语义机制:** 提供独立于传统 CRUD 的多维数据集模型（DataSource, Dataset, Field, Metric）。
2. **安全可控的查询编译:** 提供灵活但不失控的 SQL 生成器，防止用户直接拼接产生高危 SQL 注入，配合现有数据权限执行动态拦截。
3. **无缝融合现有底座:** 直接复用 MuYun 已有的组织/角色体系（`BaseScaffold`, `AuthorizationService`）、菜单平台（`ModuleController`）以及运行时能力。
4. **一次配置，多端复用:** 报表/看板定义一次，可以通过不同策略（挂载菜单、动态 iframe 嵌入或纯 API 接口）对外发布。

## 2. 范围边界

### 2.1 包含在本次范围内（MVP 及早期阶段）
- **数据源接入 (DataSource):** 优先重点适配且仅支持 PostgreSQL（含其视图、实体表及受控的参数化 SQL）。
- **语义模型 (Dataset / Field / Metric):** 以表驱动的字段抽取配置、衍生维度定义与常见聚合方式配置（Sum/Count/Max/Min 等）。
- **单表及受限多表联查:** 主子表的左连接，轻量级联合查询验证。
- **可视化单元 (Report / Widget):** 对接常见的基础图表渲染定义（折线、柱状、饼图、指标卡、数据透视表基础版）。
- **仪表盘组合 (Dashboard):** 基于 Grid 布局的多图表拼装和全局维度筛选器。
- **权限与发布治理 (Publish & Security):** 报表可作为业务菜单发布在系统中，基于现有部门/机构/角色的动态维度注入以行级过滤数据。

### 2.2 不包含在本次范围内（未来迭代/非目标）
- **海量异构数据源直连:** MySQL, Oracle, ClickHouse 等暂不在一期计划内（留出 Connector SPI 抽象即可）。
- **自研复杂 ETL 流水线:** 数据清洗、复杂的宽表物化等功能由专业中台工具外置保障，本品更偏展现场景。
- **自研渲染库:** 不自己实现图形算法，完全输出标准结构（如兼容 Echarts 系列的 JSON Schema）。

## 3. 用户角色与核心场景

### 3.1 用户角色
| 角色名称 | 对应背景 | 主要职责 |
| :--- | :--- | :--- |
| **平台系统管理员** | 具有最高权限的系统维护者 | 配置物理数据源(连接池)、监控查询耗时与异常日志、管理系统级功能权限分配。 |
| **BI 开发者 / 数据专员** | 了解一定底层数据结构的梳理者 | 把物理表映射成“数据集(Dataset)”和“指标(Metric)”，规制可用的字段边界；把控全局性能。 |
| **业务分析人员 (分析师)** | 懂运营指标的业务中坚 | 直接利用配好的数据集拖拽/选择字段，制作 Report / Widget，并将其拼装成 Dashboard，设置发布策略。 |
| **终端查看人员** | 被授权的管理层或一线员工 | 登录 MuYun 端点或通过嵌入链接预览看板，进行联动筛选和数据下钻，仅查询权限，没有编辑能力。 |

### 3.2 核心业务主干流程
1. **数据准备:** 管理员录入并测试通过 `PostgreSQL` 数据源。
2. **建模归一:** BI 开发者选择具体的 Schema 和 Table 并自动抽取字段，标注出哪些是只读的“维度(Dimension)”，哪些是可计算的���指标(Metric)”。
3. **数据权限绑定:** 开发者在数据集中定义行级过滤规则（结合 MuYun 当前角色的当前机构 `id_at_org_organization`）。
4. **可视化定义:** 业务分析师新建报表（Report），选取图表类型（如柱状图），将时间维度推入 X 轴，销售额指标推入 Y 轴，进行预览。
5. **仪表盘组装:** 分析师创建 Dashboard，将多个 Report 拖入网格并保存。
6. **发布订阅:** 分析师配置发布路由，将Dashboard 以菜单节点的形式挂入 MuYun 的 `MenuSchema` 中。
7. **终端查阅:** 用户登录后，看到新的带角标的目录，点开浏览并执行运行时的条件过滤过滤。

## 4. 功能需求详细说明

可将整体实施分为三个功能领域：“BI平台管理层（配置侧）”、“BI分析编译层（内核侧）”与“BI运行时层（消费侧）”。

### 4.1 BI 管理端配置层 (muyun-bi-platform)
*以 MuYun 现有 Scaffold 的模块形式体现。*

- **FR-P-01 数据源管理:** 维护数据源，增删改查及联通性测试功能。
- **FR-P-02 数据集管理 (Dataset):**
  - 支持“实体表”模式和“预编译SQL视图”模式。
  - 自动抽取解析表列到 DatasetField。
  - 支持配置基于组织/部门的行级过滤策略 (`j_auth_strategy`)。
- **FR-P-03 字段与指标字典 (Metrics & Field Schema):**
  - 支持设置别名、可见性、格式化规则（货币化、百分比）。
  - 支持定义纯扩展指标表达式（例如 `"sum(fee)/count(id)"`），后端做严格语法树审查。
- **FR-P-04 报表与看板管理:**
  - 维持图表的元信息配置存取 (`j_query_schema`, `j_render_schema`)。
  - 对 Widget 的引用绑定管理。
- **FR-P-05 挂载与发布配置:**
  - 类似现有模块菜单注册拦截机制，发布后的报表可指派对应角色访问限制。

### 4.2 BI 分析编译内核层 (muyun-bi)
- **FR-C-01 查询引擎请求接口:** 接收 JSON 化的多维组合请求（BiQueryRequest）。
- **FR-C-02 SQL 解析与防御编译器:** 将基于抽象 Dataset 和 Dimension+Metric 的请求动态转换为合法的 SQL，校验一切标识符以防止非白名单注入。
- **FR-C-03 动态权限熔入:** 核心执行器在生成 WHERE 子句时，需强制结合当前请求的 `ApiRequest` 上下文（含用户的标识及权限管辖域），注入类似于 `AuthorizationService.getAuthCondition()` 的语句。
- **FR-C-04 查询降级与保护:** 强制控制数据行数限制(Limit)、复杂关联限制以及查询超时的截断，保证不因恶意或高复杂配置拖垮全局数据库。

### 4.3 BI 运行时消费层 (muyun-bi-runtime)
- **FR-R-01 运行时鉴权接管:** 支持通过 Session / Gateway Token 获取身份。并结合配置发布时指派的角色，判定对当前图表的查阅权限。
- **FR-R-02 Dashboard 数据投递:** 向前端下发纯粹的可图表化结构，不带后端物理名，仅带用于 Echarts/AntV 兼容的渲染骨架。
- **FR-R-03 导出能力 (复用 IFileAbility):** 支持将当前 Dashboard 选定区域查询结果异步落地并返回 Excel/CSV 下载链接。

## 5. 权限模型与安全性 (重点设计)

为了无缝贴合 MuYun 已有成果，本模块权限不重新造轮子，分为正交的两层：

### 5.1 资产配置权限 (功能权限)
- **概念:** 哪些人能管理数据源、查看并变更 Dataset 结构、谁有权改图表？
- **实现方案:** 与 MuYun 系统自带的 `AuthorizationService` 和 `ModuleAction` 高度融合。各管理菜单内置诸如 `design, publish, delete` 操作，普通业务分析师仅授予针对 Dashboard 的 `design` 和 `publish`，剥夺对 Dataset 的 `update` 权限。

### 5.2 消费数据权限 (数据行级权限)
- **概念:** 同一张大区的“销售大盘”，北京区经理登入只看见北京的聚合数？
- **实现方案:**
  1. 在 Dataset 的扩展策略配置 `j_auth_strategy` 中，定义“本数据集的 `region_id` 映射到系统平台用户归属的地区节点”。
  2. 每当 Query Compiler 接到当前查询请求时，它调取 `AuthorizationService` 对该用户的判定，将其替换为 `WHERE region_id = 'xxx'`。
  3. 保留对超级管理员 (`config.isSuperUser(...)`) 开启全开放查询 (`1=1`) 逻辑的复用。

## 6. 技术规格与非功能需求

### 6.1 扩展架构要求
建议的工程拆分形式：
1. `muyun-bi`（承载 `BiQueryCompiler`, `BiExecutionService` 等真正逻辑，无业务拦截）。
2. `muyun-bi-platform`（承载管理配置的 API 控制器，集成 `BaseScaffold`）。
3. `muyun-bi-runtime`（对外暴漏安全渲染的只读视图接口，受 `GatewayRuntimeProvider` 环境拦截）。

### 6.2 性能目标 (非功能)
- **响应时间:** 后台非庞大聚合查询，SQL构造及鉴权阻力在 20ms 以下增加。
- **并发与限流:** 单个请求限制最大返回纪录(如配置为最多返回一万行用于前端汇总或仅取前100个聚合度分组)；复杂查询依赖 Quarkus 的背压或响应式设计以减轻对线程池的压榨。

### 6.3 审计与日志
基于 `LogBaseController`：
- 对任何修改 Dataset 与数据源的动作产生审计日志（记录操作人与内容对比）。
- 定期对复杂或��行时间超过 3s 的报表进行慢日志（Slow Query Log）标注用于性能追踪。

## 7. 里程碑计划与验收标准

### 7.1 里程碑规划 (MVP - M1 - M2)

| 阶段 | 预期时间 | 里程碑目标 | 功能摘要 |
| :--- | :--- | :--- | :--- |
| **MVP (基础贯通)** | 第一阶段 | 跑通核心引擎。 | 表建立、单表数据集管理、简单 JSON 查询模型驱动出基础聚合 SQL。 |
| **M1 (可视化集成)** | 第二阶段 | 图表、报表展现。 | 业务人员可通过接口获取图表所需标准报文（兼容某一图表库）；实现行级权限拦截对接工作。 |
| **M2 (平台化治理)** | 第三阶段 | 看板装配发布。 | 多图表合成 Dashboard；整合发布到现存 MuYun 菜单系统；加入 CSV 导出依赖；支持网关安全集成。 |

### 7.2 验收标准
1. **可用性体验:** 能够利用现有体系登录并无缝调取新增 BI 管理页面不发生突兀；数据连接能够稳定读取指定库表结构。
2. **隔离性:** 即使业务组撰写恶意 JSON 拖拽请求，生成的 SQL 必须保证在编译阶段失败（包含语法非法标识符抛出），避免注入影响。
3. **数据隔离验收:** 使用管理员帐号和某地区基层帐号查看同一个发布出的 Dashboard 返回各司其职的真实限制结果，不能越权读取。
4. **编译质量:** 后台无错误 Warning 并满足基本 Sonar Qube 中 Muyun 要求的常规规则限制。

## 8. 潜在风险与应对预案

- **风险 1：动态 SQL 引发的系统性能灾难**
  - *应对:* 必须建立最大聚合结果返回量拦截（Max Result Sets Limit）与默认 SQL 语句 `TIMEOUT` 执行机制控制。
- **风险 2：BI权限与现有权限存在耦合冲突**
  - *应对:* 坚守权限分离——将操作按钮的访问归口回系统现有 Action 配置，数据访问拦截交由编译层按预设白名单合并过滤生成，不要混淆。
- **风险 3：脱离后端优先宗旨的重度开发**
  - *应对:* BI 初版极力避免过早去搭建花里胡哨的操作面板，首先夯实接口抽象与协议层，允许前端仅用普通表单传入 JSON Schema 的方式跑通主流程。
